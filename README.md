# 規格驅動開發倉庫 (Spec-Driven Development Repo)

> 核心理念：**文件是「原始碼」，程式碼與硬體產出是「編譯產物」。**
> 只要保留 `00_` ~ `04_` 的文件，即使刪除 `src/` 與 `hardware_build/`，
> 也能依據文件重新生成一份**功能等價**且**通過所有驗收測試**的成果。

---

## 為什麼這樣能「不靠程式碼也能重建」

還原不是位元級複製，而是**功能等價還原**。要成立，文件必須鎖住三個「決定性錨點」：

| 錨點 | 軟體 | 硬體 | 存放位置 |
|------|------|------|----------|
| 1. 意圖 | 要解決什麼問題、給誰用 | 同左 | `01_requirements/PRD.md` |
| 2. 結構/契約 | 資料模型、API 合約 | 腳位、時序、電氣規格、BOM | `01_requirements/ERD.md`、`02_contracts/` |
| 3. 正確性 | 自動化測試 | 量測/驗證程序 | `03_acceptance/` |

外加 **ADR（架構決策紀錄）** 鎖住「為什麼這樣做」，避免每次重建時 AI 做出不同的架構選擇。

## 資料夾結構

```
.
├── 00_charter/          啟動與規劃（範疇、時程）
├── 01_requirements/     需求與設計（PRD、ERD、ADR、UI）
├── 02_contracts/        決定性錨點（DB schema、API、硬體規格）— 重建的關鍵
├── 03_acceptance/       驗收測試 = 可執行/可量測的規格
├── 04_ops/              部署與維運（CI/CD、runbook）
├── src/                 軟體產物（可拋棄，由文件生成）
└── hardware_build/      硬體產物（原理圖、PCB、韌體，由文件生成）
```

## 協作循環（與 Claude Code 一起）

1. **規劃/需求**：你講想法 → 我寫成結構化 PRD / ERD / ADR。
2. **契約**：確認 schema / API / 硬體規格 → 我產出 `02_contracts/` 檔案。
3. **驗收**：定義「怎樣算對」→ 我轉成 `03_acceptance/` 的測試。
4. **實作**：你說「依文件生成」→ 我**只讀 `01`~`03`** 生成 `src/` 與 `hardware_build/`。
5. **驗證**：跑測試 / 量測，證明還原成功。

## 文件慣例

- 每份文件**開頭都有 frontmatter**（版本、狀態、關聯 commit），用來雙向追溯文件↔程式碼。
- 圖表用 **Mermaid**（純文字、可版控、我可直接讀）。
- 契約檔（schema/API/腳位）用**業界標準格式**（SQL / OpenAPI / CSV），確保無歧義。
- 每次「文件變更 → 重新生成」都是一個 Git commit，commit message 註明對應的文件版本。
