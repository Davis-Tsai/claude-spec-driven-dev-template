# 逆向規格化操作步驟 (Reverse-Spec Checklist)

> 當要把「既有實作」文件化為規格時，依此步驟走。
> 搭配 `CLAUDE.md §4.5`（規則）與 `charter/reverse-spec-provenance.md`（記錄）。

## 前提原則（最重要）
- **as-built 程式碼＝最高真相**：程式碼 > 註解/檔頭 > 舊設計文件/PDF。三者衝突時，以**實際會執行的程式碼**為準。
  （常見坑：檔頭/註解描述的是**被撤銷的舊設計**，例如「連發 N 包」實際已改單發。）
- 逆向文件一律先標 `審核中`，**禁止自行標 `已定案`**。
- 明確區分「**目標值 vs 保證值**」「**已實作 vs 進行中(WIP)**」。

## 步驟

### A. 準備
- [ ] 確認既有專案位置與範圍（軟體 / 硬體 / 整合）。
- [ ] 建立 `reverse-spec-provenance.md`，填「0 適用聲明」「1 來源清單」「2 方法」。

### B. 萃取
- [ ] 讀主文件 + 原始碼 + 驗收/報告；**以程式碼校正文件的說法**。
- [ ] 可平行分工（產品/需求、硬體、軟體介面/驗收）加速。

### C. 填寫規格（狀態＝審核中）
- [ ] 每條規格標**出處**（哪個檔/文件）。
- [ ] 具體數值（腳位、頻率、封包欄位、門檻、誤差）逐一對照原始碼。
- [ ] WIP/未實測項明確標註，不當成已定案。
- [ ] 用不到的維度（如無 DB/REST）標「不適用」並改用合適契約（如封包/序列協定）。

### D. 覆蓋率矩陣
- [ ] 在 provenance §3 列「原始碼項目 → 文件位置」，露出缺口。
- [ ] 估算覆蓋率。

### E. 獨立對抗式複核（不可省）
- [ ] 由**獨立**一輪（另一個 agent／人）反查：**無臆造**（文件有、碼無）、**無遺漏**（碼有、文件缺）。
- [ ] 差異記入 provenance §4；**修正對應文件**後回填處置。

### F. 簽核
- [ ] 懂專案的人核對 → 在 provenance §6 簽核 → 才把相關文件由 `審核中` 升 `已定案`。

> （選配・最強）**往返再生測試**：只靠文件重生程式碼並通過原驗收，證明規格足以重建。成本高，有能力時再做。
