# 逆向規格化溯源記錄 (Reverse-Spec Provenance)

> **用途**：當本專案的規格是從「既有實作」逆向萃取而來時，用這份記錄**證明文件忠於原始碼**，
> 並讓未來的人能自行判斷可信度（而不是只相信 AI）。
> **適用性**：若本專案是全新正向開發（規格先於程式碼），本檔標 `不適用 (N/A)` 即可。
>
> 逆向的信任問題與正向相反：**程式碼才是真相，文件必須被證明忠於它**（見 `CLAUDE.md §4.5`、`design-decisions.md H`）。

## 0. 適用聲明
- 規格來源：☐ 全新正向開發（本檔不適用）　☐ 逆向萃取自既有實作（往下填）
- 既有專案位置：__________

## 1. 來源清單 (Sources)
> 逆向所依據的既有檔/文件與版本、日期。
| 來源 | 版本 / 日期 | 涵蓋內容 |
|------|-------------|----------|
| 例：Firmware/.../imu_if.c | git \<hash\> / YYYY-MM-DD | IMU 設定、積分 |

## 2. 萃取方法 (Method)
- 由誰 / 什麼做（人工 / AI 代理）、何時、如何交叉比對：__________

## 3. 覆蓋率矩陣 (Coverage Matrix)
> 原始碼的每個重要項目 → 文件位置。「缺口」欄有值＝尚未涵蓋。
| 原始碼項目（模組 / 腳位 / 命令 / 資料欄位…） | 文件位置 | 缺口 / 備註 |
|------|----------|-------------|
| 例：0x02 結果封包 | contracts/interfaces.md §1 | — |

- 覆蓋率估計：____%（已涵蓋項 ÷ 應涵蓋項）

## 4. 獨立對抗式複核 (Independent Verification)
> 由**獨立**一輪（另一個 agent 或人）反向查核，記錄差異。
- 複核者 / 日期：__________
- **臆造項**（文件有、原始碼查無）：（無 / 列出）
- **遺漏項**（原始碼有、文件未收）：（無 / 列出）
- 處置：（已修正 / 待處理）

> 逆向文件預設 `審核中`；由懂專案的人核對後，才可把相關文件升 `已定案`。
