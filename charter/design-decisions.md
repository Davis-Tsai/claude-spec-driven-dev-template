# 設計決策與限制總覽

> 這份文件讓你**一次讀懂這套模板為什麼這樣設計、以及每個決策帶來的限制**。
> 想知道「為什麼要這樣做」「這樣做有什麼代價」時，看這裡。
> 精簡的定案清單見 `charter/open-questions.md`；每條規則的操作細節見 `CLAUDE.md`。
>
> 格式：每項 = **決策** ｜ **為什麼** ｜ **限制／代價**（你要接受的取捨）。

---

## A. 核心理念

### A1. 規格驅動：文件是原始碼，程式碼是產物
- **為什麼**：讓「不靠程式碼、只靠文件就能重生」成為可能。
- **限制**：所有功能改動要先走文件，比「直接寫程式」多一道手續。

### A2. 只能「功能等價還原」，不是位元級複製
- **為什麼**：同一份文件生成兩次，變數名/檔案切分會不同，但行為一致。
- **限制**：不要期待重生出「一模一樣」的程式碼；**保證的是通過同一組驗收測試**。

---

## B. 軟硬體策略

### B1. 韌體＋規格可重生；PCB／原理圖一起進 Git 保存，不重生
- **為什麼**：佈線、EMC、類比電路高度依賴實體調校，無法純文字還原。
- **限制**：硬體的「實體設計檔」要當成資產保存在 `hardware_build/`，不能刪了指望重生。

### B2. 硬體驗收用人工量測，不做自動測試
- **為什麼**：硬體正確性要靠示波器/電流表等實際量測。
- **限制**：硬體的「還原成功」無法像軟體自動證明，需人工記錄實測值。

### B3. 一份模板通吃軟體/硬體/軟硬整合
- **為什麼**：不用維護多份模板。
- **限制**：純軟體或純硬體專案會有空資料夾；需在 `scope.md` 宣告專案型態，並把用不到的文件標「不適用」。

---

## C. 真相與結構

### C1. `contracts/` 是唯一真相；生成程式碼只讀 requirements + contracts + acceptance
- **為什麼**：避免多處定義資料模型造成不一致；避免 AI 參考舊程式碼延續寫法而偏離文件。
- **限制**：`ERD.md` 的圖只是導讀，衝突時一律以 `contracts/` 為準；改資料模型要改 `contracts/`。

### C2. 版本交給 Git；frontmatter 只留「狀態」
- **為什麼**：手寫版本號/日期容易失真，Git 本來就是版本史。
- **限制**：要看「這份文件的歷史」得用 `git log`，文件內不記版本。

### C3. 資料夾依功能分類（不用階段編號）
- **為什麼**：文件在生命週期會反覆修改，功能分類比「一次性的階段」耐用。

---

## D. 模板可攜與初始化（Q4 + Bootstrap）

### D1. 用 `CLAUDE.md` 當「AI 操作手冊」，讓模板自帶大腦
- **為什麼**：Claude Code 開新對話會自動載入 `CLAUDE.md`，複製到新專案規則就跟著走。
- **限制**：**僅對 Claude Code 有效**。用其他 AI（ChatGPT/Gemini/Cursor）不會自動讀。

### D2. 動手開發前先做版控自檢
- **為什麼**：確保新專案一開始就在乾淨的本地 Git 下。
- **內容**：沒有 repo → `git init`；繼承了模板 `.git` → 強烈建議重置；連 GitHub → **完全交給使用者**，AI 不碰。

### D3. 複製時不要帶 `.git`；小心隱藏檔
- **為什麼**：帶 `.git` 會污染模板歷史、push 推錯 repo。
- **限制**：`.githooks/`、`.gitignore` 是隱藏檔容易漏複製；漏了 hook 防護會失效（AI 初始化時會提醒）。

---

## E. 狀態流轉與變更管理（Q1）

### E1. 狀態：草稿 → 審核中 → 已定案（＋修改中／不適用）
- **升級權限**：`草稿→審核中` AI 可做；`審核中→已定案` **只有使用者**能按。
- **為什麼**：定案是人類把關的閘門，關係到「何時能開始生成程式碼」。

### E2. 定案前 AI 先跑「定案前檢查」
- **為什麼**：確保追溯無缺口、契約語法有效、硬體規格不衝突，「已定案」才可靠。

### E3. 已定案文件不可直接改，走變更管理
- **為什麼**：讓將來能看到完整修改過程，且功能文件永遠是最新。
- **流程**：進「修改中」→ 與 AI 討論 → 同步更新 PRD/ERD/契約/驗收 → 記一筆到 `changes/change-log.md` → 回「已定案」。
- **限制**：改已定案的東西比較「重」，要留紀錄、要同步多份文件。

---

## F. 文件與程式碼同步（Q2）

### F1. 文件優先 (spec-first)，禁止繞過文件直接手改 `src/`
- **為什麼**：一旦允許程式碼偷跑，「文件即真相」就會失效。
- **限制**：臨時手改了程式碼，**必須立即回補**文件與 change-log，否則算漂移。

### F2. 靠 acceptance 測試判定「程式碼是否符合契約」
- **為什麼**：測試通過是比肉眼比對更硬的保證。

### F3. pre-commit hook 自動擋不同步
- **為什麼**：commit 前自動跑測試，沒過就擋，從機制上防漂移。
- **限制**：測試指令集中在 `acceptance/run-tests.sh`，**技術棧定案後要填入**才會真正生效；別隨意 `--no-verify` 跳過。

---

## G. 技術棧（Q3）

### G1. 模板技術中立；實際選型時各記一則 ADR
- **為什麼**：模板不寫死技術才通用；ADR 鎖住「為什麼選這個」，重生才不會選到不同技術而不等價。
- **限制**：選定後要記 ADR，並把測試指令填進 `run-tests.sh`。
